# M9.2 — Architecture Review: Care Feedback Loop & Outcome Intelligence

**Status:** Implemented (reporting foundation) — see `docs/M9.2_IMPLEMENTATION_PLAN.md` + `docs/M9.2_OUTCOME_SCHEMA.md`  
**Mode:** Outcome reporting only — no CARE_SEND enable, no production Care rollout, no M9.3  
**Mode:** Design + plan — no code, no flag enable, no M9.3  
**Depends on:** M9.0 Care module + M9.1 ops package; CARE flags remain OFF by default  

---

## Goal

Add a **Care outcome feedback** layer after M9.0/M9.1 so operators can:

1. See whether care events **succeed** (delivery + downstream response)  
2. Capture **customer response signals** (without turning OA into a trivia bot)  
3. Feed **policy improvement** (eligibility thresholds, copy, throttle)  
4. Keep outcomes in **Care** — never merge into Case result-send notification state  

M9.2 does **not** add new care campaigns and does **not** enable production CARE sending.

---

## Current architecture

| Layer | State |
|-------|--------|
| Case | Ops SSOT; result notification lifecycle unchanged |
| Customer | Identity only; M8 flags human-gated |
| Care | `care.reinspection_6mo` + M9.1 runbook; CARE flags OFF |
| Care Audit | Separate file (± optional Notion) store |
| Runtime | No customer-facing Care sends enabled |

---

## Architecture principle (locked)

```text
Case history
    ↓
Care Policy
    ↓
Care Event
    ↓
LINE delivery
    ↓
Care Audit
    ↓
Outcome signals
    ↓
Care improvement (ops / policy params — not Case rewrite)
```

Outcome intelligence is a **Care-domain concern**. It observes; it does not own Booking/Workflow/Offer/Feedback/Report/result-send.

---

## 1. Outcome signal catalog

### Delivery outcomes (from Care Audit — already partially present)

| Signal | Source | Meaning |
|--------|--------|---------|
| `delivered_sent` | Audit `status=sent` | LINE push accepted / mock ok |
| `delivered_failed` | Audit `status=failed` | Push failed |
| `skipped_*` | Audit `status=skipped` + reason | Not sent (anchor, consent, no LINE, …) |
| `idempotent_suppress` | `already_sent` | Duplicate period blocked |

### Response outcomes (new — design)

| Signal | Capture method (preferred) | Notes |
|--------|------------------------------|-------|
| `cta_book_clicked` | Booking URL with care UTM / `careAuditId` query (Framer/booking already Case-creating) | Best effort; not all clicks attributable |
| `cta_postback_ack` | Optional LINE postback `care_ack` / `care_book` on care message quick-reply | Additive; must not break OA intent priority |
| `rebook_within_window` | Case create after care send for same Customer/LINE within N days | Derived from Case history + Care Audit join |
| `opt_out_signal` | Customer `consentLine=false` after care, or explicit care opt-out postback | Steward review; no auto-merge |
| `no_response` | No attributable signal within observation window | Default |

**Forbidden as primary signals:** name matching; scraping chat free text as identity; writing outcomes onto Case `notificationStatus`.

## 2. Ownership boundaries

| Concern | Owner |
|---------|--------|
| Result-send lifecycle | **Case** (unchanged) |
| Care send + Care Audit | **Care** |
| Outcome records / aggregates | **Care** (`CareOutcome` or audit extensions) |
| Identity / consent | **Customer** |
| New booking Case after CTA | **Case** (create path unchanged) |
| Policy parameter changes | **Ops + Care policy** (human-gated; config/env or documented constants) |

## 3. Storage design (preferred)

Extend Care domain — **do not** add reminder outcome fields to Case notification props.

### Option A (recommended for M9.2)

Extend `CareAuditEvent` with outcome fields (additive):

```text
outcomeStatus          # unknown | no_response | cta_clicked | rebooked | opted_out | ...
outcomeAt
outcomeSource          # line_postback | booking_utm | derived_rebook | manual
linkedCaseIdAfter      # if rebook attributed
observationWindowEndsAt
```

### Option B

Separate `CareOutcomeEvent` rows keyed by `careAuditId` / `idempotencyKey` (cleaner history; more tooling).

**M9.2 architecture preference:** start with **Option A** for the single event type; graduate to Option B if volume/history demands.

File reports remain first-class while CARE flags OFF; Notion optional.

---

## 4. Feedback loop (how improvement works)

```text
Weekly cadence (M9.1)
  → outcome rollup report (sent / failed / skip mix / CTA / rebook rate)
  → human review
  → adjust CARE_REINSPECTION_DAYS, copy version, throttle, limit
  → next dry-run / limited SEND (still M9.1 gates)
```

**No automatic policy mutation** in M9.2 (no ML auto-tuning). Intelligence = **observable metrics + human decision**.

---

## 5. Rollout / flags

M9.2 adds **observation** capability that works on dry-run audits and any future sends.

Proposed flags (design only; default false if implemented later):

```text
CARE_OUTCOME_TRACKING=false   # record/derive outcomes
CARE_OUTCOME_REPORT=false     # optional CLI report generation
```

Independent of `CARE_LIFECYCLE_SEND`. May analyze historical dry-run/sent audits with tracking ON and SEND OFF.

Does **not** enable CARE_SEND or Customer Domain flags.

---

## 6. Privacy & PII

- Continue hashing LINE ids in shared logs (`destinationIdHash`)  
- Outcome reports: aggregate counts first; samples PII-safe  
- No storing raw chat transcripts as Care outcomes in M9.2  

---

## 7. Risks

| Risk | Mitigation |
|------|------------|
| Polluting Case notification state | Separate Care outcome fields only |
| Mis-attributed rebooks | Conservative window + Customer/LINE exact join only |
| OA postback conflicts with M7 intents | Dedicated `care_*` postback prefix; priority below feedback token |
| Building “analytics platform” scope | Single-event rollups + CLI report only |
| Enabling SEND under guise of analytics | Explicit non-goal; M9.1 gates unchanged |

---

## 8. Non-goals (M9.2)

- New care campaigns  
- Production CARE_SEND enablement  
- Customer identity redesign / fuzzy match  
- Auto-tuning eligibility without human approval  
- Dashboard/Framer contract redesign (beyond optional UTM on booking URL)  
- Moving Offer/Workflow/Feedback/Report under Care or Customer  
- M9.3
