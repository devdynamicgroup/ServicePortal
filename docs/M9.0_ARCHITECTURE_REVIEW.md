# M9.0 — Architecture Review: Customer Care Lifecycle Events

**Status:** Architecture approved for planning — implementation plan in `docs/M9.0_IMPLEMENTATION_PLAN.md`  
**Mode:** Design + plan — no code, no flag enable, no M9.1  
**Chosen topic:** Event-driven care lifecycle (reminders + notification policy) on top of M8 identity  

**Why this topic (not others):**

| Candidate | Deferred reason |
|-----------|-----------------|
| Remove Case LINE / move ops to Customer | Violates M8.9 permanent rules; needs separate ADR |
| Auto-merge / fuzzy | Explicitly forbidden |
| “Just enable M8.8 flags” | Ops, not architecture |
| Durable metrics platform | Valuable but secondary to product care vision |
| **Care lifecycle events** | Matches `CUSTOMER_COMMUNICATION_ARCHITECTURE.md`; extends Case events + Customer identity without ownership migration |

---

## 1. Goal

Introduce a **Customer Care Lifecycle** layer that schedules and sends **event-driven** LINE care messages (starting with **6-month re-inspection reminder**), using:

- **Case** as source of operational truth (last inspection / result-sent timing)  
- **Customer** (when linked) as identity for destination resolution (via existing M8.6 notify path when enabled; Case LINE fallback otherwise)  
- A small **Notification Policy Engine** that maps `event → eligibility → message → send`

Does **not** turn LINE OA into a chatbot trivia system. Prefer push-on-event over command-driven flows.

---

## 2. Current architecture impact

| Existing | Impact |
|----------|--------|
| Case aggregate | Remains SSOT for “when was last service / result sent” |
| Customer identity (M8) | Destination resolution only; no new identity model |
| `executeSendCaseResult` / notify reader (M8.6) | Reuse destination resolution patterns; **new event types** ≠ result-send state machine |
| LINE OA intents (M8.5) | Unchanged; care pushes are outbound |
| M8.8 flags | Care sends must work with flags OFF (Case LINE) and ON (Customer destination policy) |
| Notification **state** on Case | Result-send lifecycle stays Case-owned; care events need **separate** audit fields or log (design choice below) |

### Proposed high-level flow

```text
Scheduler / trigger
  → CarePolicy.evaluate(eventType, caseId|customerId)
  → resolve LINE destination (Case LINE; Customer when READ_NOTIFY)
  → send LINE care message
  → record care delivery audit (not overwrite result-sent notification state)
```

---

## 3. Ownership boundaries

| Concern | Owner |
|---------|--------|
| “Last inspection / result ready” timestamps | **Case** |
| Water Score / report / feedback | **Case** |
| Result-send notification status machine | **Case** (unchanged) |
| Care event eligibility rules | **Care / Notification Policy** (new module — not Customer, not Offer) |
| LINE destination identity | **Customer** when flagged; else **Case** LINE |
| Message templates for care | LINE / care module |
| Booking creation from “นัดตรวจ” CTA | Existing booking URL / Case create — still Case |

**Customer does not own:** reminder schedules as operational records of “service due” — those derive from Case history.

**Case does not own:** canonical person identity (M8).

---

## 4. Risks

| Risk | L | Mitigation |
|------|---|------------|
| Confusing care send with result-send status | H | Separate audit (`careEventLog` / Case care props) — never reuse `notificationStatus=sent` for reminders |
| Spam / marketing tone | M | Care copy only; consent checks if present; throttle per Customer/Case |
| Wrong recipient | H | Same M8.6 diverge policy; flag-only rollback |
| Scheduler reliability | M | Idempotent event keys; dry-run; feature flag `CARE_LIFECYCLE_ENABLED` default OFF |
| Premature dependency on READ_NOTIFY | M | Destination adapter works Case-first |
| Scope creep into loyalty/CRM | M | M9.0 = reminder + policy skeleton only |

---

## 5. Migration strategy

### Phased (design)

| Phase | Content |
|-------|---------|
| M9.0a | Architecture + policy interface + event catalog (6-month reminder first) |
| M9.0b | Offline/dry-run eligibility scanner (no send) |
| M9.0c | Flagged send path + audit; Case LINE destination |
| M9.0d | Optional Customer destination via existing notify reader when `READ_NOTIFY` on |
| Later | Lab-ready push hardening; filter-change reminders (same engine) |

### Feature flag (proposed)

```text
CARE_LIFECYCLE_ENABLED=false   # master
CARE_LIFECYCLE_SEND=false      # actual LINE push
```

Independent of `CUSTOMER_DOMAIN_*`. Does not auto-enable Customer flags.

### Data

- Prefer **derived** eligibility from Case `resultSentAt` / `serviceCompletedAt`  
- Additive audit only; no rewrite of historical notification state  
- No Customer ownership of Cases  

### Rollback

- Disable care flags → no sends  
- Result-send and OA history unaffected  
- No data rollback required  

---

## 6. Non-goals (M9.0)

- Removing Case LINE fields  
- Moving Offer / Workflow / Feedback / Report / Notification **state** to Customer  
- Auto-merge / fuzzy identity  
- Enabling M8 Customer read flags as part of M9.0  
- Full marketing automation / broadcast campaigns  
- Replacing token bootstrap (`fb-*` / `rpt-*`)  
- Rewriting LINE webhook contract  
- Dashboard/Framer contract breaks

## 7. Open decisions (lock before implement)

2. Scheduler host: cron script vs in-app interval vs external  
3. Idempotency key shape: `care:6mo:{caseId}:{period}`  
4. Consent: require `consentLine` on Customer when linked?
