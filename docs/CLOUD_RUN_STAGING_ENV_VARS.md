# Cloud Run Staging — Required Environment Variables

Deployment handoff document for whoever runs the actual `gcloud run deploy` for
`serviceportal-staging`. Generated by reading the current repository
(`server.js`, `config/`, `api/`, `services/`) for real `process.env.*`
references — not reconstructed from memory or from a prior audit report.

**No secret values, tokens, or credentials appear in this file. Key names
only.** Where a value cannot be determined from source (because it's an
external credential), this file says `Not determinable from source`.

---

## 1. Required for application startup

Missing these causes `server.js` / `services/app-auth.js` to log a `[FATAL]`
line and call `process.exit(1)` before the process accepts any traffic.

| Variable | Required | Purpose | Staging note |
|---|---|---|---|
| `AUTH_USERS_JSON` | Yes | JSON array of portal login users (`services/app-auth.js`) — the server refuses to start without it unless `AUTH_ALLOW_DEV_USERS=true` is also set on a non-production runtime | Not determinable from source (values are real staff credentials). Use a separate staging-only JSON, not the production value. |
| `AUTH_SESSION_SECRET` (or `SESSION_SECRET`) | Yes, when `isProductionRuntime()` is true | HMAC key signing the stateless session cookie | See **Cloud Run deployment notes** below — Cloud Run does not automatically count as "production" the way Render does, so this is only enforced if `NODE_ENV=production` is explicitly set. |
| `NODE_ENV` | Effectively required | Selects production-safe behavior in `services/app-auth.js` (`isProductionRuntime()`) and `server.js` | Not itself a secret. On Render this is set automatically; on Cloud Run it must be set explicitly — see notes below. |

## 4. Production/ops-only — not a Cloud Run runtime requirement

These exist in the codebase but are read either by Render's own platform
integration or by local operator/test scripts (`scripts/*.js`, excluded from
the Docker image by `.dockerignore`). The deployed Cloud Run app does not need
any of these to function.

| Variable | Where it's read | Why it's not a Cloud Run requirement |
|---|---|---|
| `RENDER`, `RENDER_SERVICE_ID` | `server.js`, `services/app-auth.js` | Render-platform-set signals used only to detect "am I running on Render." Their *absence* on Cloud Run is expected and correct — it is not something to replicate. |
| `RENDER_GIT_COMMIT` | `api/ops-routes.js` | Render-specific build metadata shown on the ops/health endpoint. Harmless if unset on Cloud Run — the field just reads empty. |
| `RENDER_EXTERNAL_URL` | `api/line-routes.js`, `api/cal-routes.js`, `services/client-feedback.js`, `services/url-builder.js` | Render's own external-URL convention. On Cloud Run, set `PUBLIC_BASE_URL` instead (see feature table above) — the code already prefers `PUBLIC_BASE_URL` first. |
| `RENDER_API_KEY` | Only in `scripts/*.js` (local ops scripts that call Render's own API to read env vars / trigger checks) | Not referenced anywhere in `server.js`, `api/`, or `services/`. It is an operator credential for managing the *Render* service, not something the running application itself uses. |
| `E2E_BASE_URL`, `E2E_USERNAME`, `E2E_PASSWORD` | Only in `scripts/*.js` (QA/E2E scripts) | Test-script inputs, not application runtime config. |
| `VERIFY_LINE_DRY_RUN` | Only in `scripts/verify-line-linking.js` | Script-only. |
| `USER`, `USERNAME` | Only in `services/migration/customer-backfill.js`, for an audit-trail "run by" label on a manual migration script | Not read by any request path. |

## Cloud Run deployment notes

- **`PORT` is managed by Cloud Run/the runtime.** Do not set it manually — Cloud Run injects it, and `server.js` already reads `process.env.PORT` and binds `process.env.BIND_HOST || '0.0.0.0'`. The app must keep listening on the runtime-provided `PORT`.
- **`OCR_SERVICE_URL` should point at the existing OCR Cloud Run service** (`https://ocr-service-478904721531.asia-southeast1.run.app`), already live in the same GCP project. This is an operational URL, not a secret.
- **All secrets must be injected by the deployment mechanism** (Cloud Run environment variables / Secret Manager), never committed to the repository or baked into the image. `.dockerignore` already excludes `.env` and `.env.*`.
- **Do not commit secret values.** This document intentionally lists variable names only.
- **Mutation-capable production credentials (`NOTION_API_KEY`, `LINE_CHANNEL_ACCESS_TOKEN`, `CAL_WEBHOOK_SECRET`) should not be exercised for staging mutation tests.** If staging needs to prove Notion/LINE connectivity, prefer a read-only check or a non-production Notion/LINE target, not a real write/send against production data.
- **`RENDER_API_KEY` is an ops/local concern, not a Cloud Run runtime requirement.** No code path in `server.js`, `api/`, or `services/` reads it — only local operator scripts under `scripts/` do, and that directory is excluded from the Docker image.
- **Set `NODE_ENV=production` explicitly on Cloud Run.** `isProductionRuntime()` (`services/app-auth.js`) treats `NODE_ENV=production` OR the presence of `RENDER`/`RENDER_SERVICE_ID` as "production." Cloud Run will never set the Render-specific variables, so without an explicit `NODE_ENV=production`, the app runs in its non-production code path — which allows an `AUTH_SESSION_SECRET` fallback and other production-only startup guards to be skipped. This is a real behavioral difference from Render, not a hypothetical.
- **Keep every `CUSTOMER_DOMAIN_*` and `CARE_LIFECYCLE_*` flag unset (or explicitly `false`) on staging**, consistent with their production state today — this document does not recommend enabling M8/M9 behavior as part of a staging deploy.
