# M8.2 — Customer Backfill Plan

**Status:** Implemented (offline tooling). Write mode requires `NOTION_CUSTOMERS_DATABASE_ID` + schema gate.  
**Flags:** All `CUSTOMER_DOMAIN_*` remain **OFF** during M8.2  
**Ownership:** Case = operational SSOT; Customer = generated identity projection

---

## Scope

**In scope**

- Offline backfill of Customer records from existing Case (Clients DB) identity fields
- Additive Case link properties (`Customer ID`, `Customer Page ID`) written only by the backfill job
- Dry-run + write + validation report
- Idempotent, restartable, reversible process under `services/migration/`

**CLI**

```bash
node scripts/run-customer-backfill.js --mode=dry-run
node scripts/run-customer-backfill.js --mode=dry-run --ensure-schema
node scripts/run-customer-backfill.js --mode=write --ensure-schema
node scripts/run-customer-backfill.js --rollback --report=tmp/customer-backfill/<runId>.write.json
```

Reports: `tmp/customer-backfill/` (gitignored)

**Out of scope**

- Dual-write, matcher engine, primary/LINE/notification Customer read
- Changing APIs, Dashboard, Framer, LINE webhook
- Moving Offer / Workflow / Feedback / Reports to Customer
- Fuzzy matching or name-based auto-merge
- Computing Lifetime Score / inventing consent

---

## Source data

| Source | Role |
|--------|------|
| Clients DB (Cases) | Sole identity source for backfill |
| Customers DB | Target for create / reuse |
| Feedback DB | Not a Customer source |

Identity inputs: Full Name, Phone, Email, Address, LINE User ID, LINE display/handle, LINE linked flags, Case Notion page id (for linking only).

---

## Prerequisites (before write)

1. `NOTION_CUSTOMERS_DATABASE_ID` configured; Customers schema synced (M8.1)
2. **Approve and add** Case additive properties (no renames):
   - `Customer ID` (rich_text) — business id mirror
   - `Customer Page ID` (rich_text) — Notion persistence link
3. Staging dry-run approved
4. Feature flags remain OFF

---

## Execution flow

```text
A. Schema gate
   Ensure Customers DB + Case link props exist

B. Dry-run (read-only)
   Scan Cases → normalize → group by exact keys → emit Validation Report
   No Customer creates; no Case updates

C. Write (ops-approved)
   For each Case (checkpointed):
     - skip if already linked and Customer exists
     - create or reuse Customer by exact match rules
     - write Case Customer ID + Customer Page ID
   Emit Validation Report

D. Validate + lock
   Re-scan consistency
   Record runId / lock marker (ops)
   Do NOT enable runtime flags
```

---

## Validation

Every run (dry-run or write) produces the Validation Report defined in  
`docs/M8.2_VALIDATION_REPORT_DESIGN.md`.

Exit criteria for write approval:

- Zero unintended duplicate Customers for already-linked Cases on re-run
- Conflicts / ambiguous matches queued, not auto-merged
- Spot-check: Offer capacity, booking create, LINE webhook still unchanged

---

## Rollback

See Rollback section in the architecture review response and summary below:

1. Stop job (flags already OFF → runtime unaffected)
2. Clear Case `Customer ID` / `Customer Page ID` written by backfill
3. Optionally archive/delete Customers with `sourceFingerprint` prefix `backfill:v1`
4. Never delete/alter Case operational fields (offer, workflow, tokens, notifications)
