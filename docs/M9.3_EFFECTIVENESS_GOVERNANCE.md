# M9.3 — Care Effectiveness Governance

**Status:** Active (governance)  
**Related:** `docs/M9.3_CARE_DECISION_RECORDS.md` · `docs/M9.3_POLICY_REVIEW_RUNBOOK.md` · `docs/M9.2_OUTCOME_SCHEMA.md`  
**Architecture:** `docs/M9.3_ARCHITECTURE_REVIEW.md`

---

## Principle

```text
Care Event → Care Audit → Outcome Signals → Human Review → Policy Adjustment
```

Effectiveness improves only through **human-approved** policy changes recorded as CDRs.  
There is **no** auto-tuning and **no** ML policy mutation in M9.3.

---

## Ownership

| Concern | Owner |
|---------|--------|
| Outcome reports | Care (M9.2; read-only consume) |
| Effectiveness review | Operator + Reviewer |
| Policy / template / timing apply | Ops after CDR `approved` |
| Incident flag rollback | On-call (M9.1 card; CDR optional after) |
| Case notification lifecycle | **Case** — never Care governance |
| Customer identity | **Customer** — unchanged |

---

## Approval workflow

```text
1. Review outcomes (runbook)
2. Draft CDR (status=draft)
3. Reviewer signs (status=approved)  ← required for policy changes
4. Operator applies changeDetail
5. status=applied
6. Dry-run / follow-up per CDR
7. If undo: apply rollback → status=reverted
```

### Human approval is mandatory for

- template version / copy  
- timing (`CARE_REINSPECTION_DAYS`, windows)  
- throttle / cron / limit guidance  
- eligibility rule adjustments  

### Not a substitute for M9.1 SEND go/no-go

A strong rebook rate or “healthy” weekly review **does not** authorize `CARE_LIFECYCLE_SEND=true`.  
SEND remains solely under `docs/M9.1_GO_NO_GO_CHECKLIST.md`.

## Immutability

| Artifact | Rule |
|----------|------|
| Historical CareAuditEvent | Do not rewrite; append-only audits stay as-is |
| Outcome measurement | May recompute in memory / reports; do not invent audit history |
| CDR instances | New files or status transitions only; do not falsify past decisions |
| Case notification fields | Never written by Care governance |

---

## Effectiveness rubric (human classify only)

| Signal | Weak | Acceptable | Strong (needs volume) |
|--------|------|------------|------------------------|
| Delivery | High unexplained fail | Mostly sent/dry_run + explained skips | Stable sent + low fail |
| Response | Almost all no_response after window | Mix with some rebook/UTM | Meaningful rebook vs organic baseline |
| Ops hygiene | Wrong anchors / mystery skips | Explained skip mix | Stable mix + clean samples |

**While SEND is OFF:** prioritize dry-run quality and skip/fail hygiene over ROI. Do not invent SEND pressure from dry-run-only metrics.

---

## Forbidden behaviors

- Automatic policy mutation from report metrics  
- ML / optimizer writing eligibility or templates  
- Storing CDRs inside Care audit jsonl  
- Enabling CARE_SEND as part of M9.3  
- Fuzzy / name-only rebook attribution in learning  
- Writing Case `notificationStatus` / `resultSentAt`  
- New care campaigns as a governance side effect
