## Architecture principles (locked)

| Domain | Owns | Does not own |
|--------|------|----------------|
| **Case** | Operational SSOT; service history; result notification state | Care policy / Care Audit / Care outcomes |
| **Customer** | Identity only (LINE / phone / email; consent) | Ops workflows; care campaigns |
| **Care** | Care policy, events, audits, outcomes, decisions (CDR) | Case result-send; Customer merge/identity expansion |

**No ownership movement** between Case, Customer, and Care.

```text
Care policy + events
    ↓
Care Audit (immutable history)
    ↓
Outcome signals (M9.2)
    ↓
Human review (cadence)
    ↓
CDR (M9.3)
    ↓
Approved controlled update
```

## Target steady-state model

Assumes launch completed via M9.4 (Checkpoint A→C → uncapped/cron). Until then, the same loop applies to dry-run / pre-SEND observation with SEND remaining gated.

### 1. Care steady-state lifecycle

```text
Launch complete (M9.4 Phase 4)
    ↓
Monitor (delivery + outcomes + complaints)
    ↓
Review outcomes (weekly / monthly)
    ↓
Create CDR (if change proposed)
    ↓
Approve policy change (Reviewer)
    ↓
Controlled update (Operator applies)
    ↓
Validate (dry-run sample and/or limited observe)
    ↓
Continue monitor
```

| Stage | Primary artifacts |
|-------|-------------------|
| Monitor | `latest.json`, pattern scanner, outcome report, fail-pause rule |
| Review | M9.1 cadence + M9.3 policy review runbook |
| Decide | CDR (`docs/M9.3_CARE_DECISION_RECORDS.md`) |
| Change | Timing / copy / throttle / eligibility **only** after CDR `approved` |
| Validate | Dry-run and/or observe window; no silent thrash |

**Incident path** interrupts the loop: rollback flags first, then investigate, optional post-incident CDR.

## 2. Optimization governance

### Allowed (CDR-gated)

| Change | Examples | Gate |
|--------|----------|------|
| Reminder timing | `CARE_REINSPECTION_DAYS`, documented windows | CDR `timing` + Reviewer |
| Copy / template | Thai care tone, `templateVersion` | CDR `template` + tone approval |
| Throttle limits | Cron frequency, default `--limit=` guidance | CDR `throttle` |
| Eligibility rules | Skip thresholds, eligibility constants | CDR `eligibility` + dry-run sample |

One material change per CDR cycle preferred (avoid stacked thrash).

### Forbidden

| Behavior | Why |
|----------|-----|
| Auto tuning from metrics | No automatic policy engine |
| ML policy mutation | Explicitly out of architecture |
| Fuzzy targeting / name match | Identity + attribution integrity |
| Identity expansion via Care | Customer remains identity-only |
| New campaigns as “optimization” | Separate future program; not M9.5 steady-state |
| Writing Case `notificationStatus` | Boundary violation |
| Using weekly “healthy” to force SEND | SEND only via M9.4 go/no-go |

## 3. Metrics ownership

### Delivery (Care ops)

| Metric | Source | Owner |
|--------|--------|-------|
| sent | Care Audit / run report | Operator |
| failed | Care Audit / LINE errors | Operator → On-call if spike |
| skipped | Run report + reason codes | Operator |
| Duplicate prevention | Idempotency index / `already_sent` | Operator (single runner) |

### Outcome (Care + Reviewer)

| Metric | Source | Owner |
|--------|--------|-------|
| response mix | Outcome report (`unknown` / `no_response` / …) | Operator drafts; Reviewer interprets |
| rebook within window | M9.2 attribution (exact id/LINE, 30d) | Care domain; Reviewer on effectiveness |
| opt-out / consent signals | Customer consent + skip reasons | Identity steward + Operator |
| complaints | Support / OA tickets | On-call first response; Operator forensics |

### Governance (Care decisions)

| Artifact | Owner |
|----------|--------|
| CDR history | Operator maintains; Reviewer approves |
| Policy change log | CDR `applied` / `reverted` statuses |
| Approvals | Reviewer (B/C-style); On-call for incidents / Checkpoint A-class decisions |

Case owners do **not** own Care metrics. Customer stewards own consent identity facts, not care campaign KPI dashboards.

## 4. Production incident model

### Severity cues

| Class | Examples | First action |
|-------|----------|--------------|
| Delivery failure | Fail-pause ≥20% with n≥5; LINE token errors | `CARE_LIFECYCLE_SEND=false` |
| Wrong recipient | Spam / wrong LINE complaint | SEND off immediately |
| Consent issue | Sent despite `consentLine=false` (bug) | SEND off; steward review; CDR after fix |
| Boundary violation | Case notification mutated by Care | SEND + ENABLED off; escalate |
| Eval instability | Cron double-fire / scan chaos | ENABLED off if needed |

### Rollback (locked — flag-only)

```text
1. CARE_LIFECYCLE_SEND=false
2. CARE_LIFECYCLE_ENABLED=false    # if evaluation / cron must stop
```

Cards: `docs/M9.4_CARE_ROLLBACK_CARD.md` · `docs/M9.1_ROLLBACK_CARD.md`

### Escalation ownership

| Role | Duty |
|------|------|
| On-call | Execute flag rollback; page Reviewer if customer-facing harm |
| Operator | Preserve Care Audit / reports / idempotency index; stop cron |
| Reviewer | Approve re-entry; require return to dry-run / checklist as needed |
| Identity steward | Consent / wrong-recipient identity follow-up |

### Explicit non-actions

- No Case rewrite to “undo” care  
- No Customer rollback / mass unlink / fuzzy merge  
- No audit deletion  
- No automatic re-enable of SEND

## 5. Operating cadence (steady state)

| Cadence | Focus |
|---------|--------|
| Weekly | Delivery mix, fail-pause, skips, duplicates, outcome report, classify (healthy / investigate / propose_change) |
| Monthly | Volume vs Case base, copy/tone, consent samples, open CDR follow-ups |
| Per deploy | Flags match intended phase; relevant fixture tests |
| Per CDR apply | Dry-run validate; observe before further changes |

SEND remains reversible at any time. Policy changes never bypass CDR.
