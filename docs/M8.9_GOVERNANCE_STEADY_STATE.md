## Goal

Define how the Customer identity domain is **governed in steady state** after M8.1–M8.8 tooling exists — whether flags are still OFF or later enabled via M8.8.

M8.9 answers:

1. Who owns identity decisions?  
2. What is the permanent dual-write / denormalization policy?  
3. What is the recurring ops cadence?  
4. What is explicitly **never** done without a new milestone?  
5. When is the M8 Customer Domain program “complete”?  

---

## Steady-state target architecture (locked)

```text
Case  = operational aggregate root
        Booking | Workflow | Offer | Feedback | Report | Notification state
        + denormalized LINE User ID (permanent fallback / safety)
        + Customer ID / Customer Page ID (link)

Customer = identity projection only
        name | phone | email | address | LINE identity | status | consent…
```

| Concern | Owner forever (M8.9) |
|---------|----------------------|
| Ops lifecycle | Case |
| Identity SSOT (logical) | Customer |
| LINE push destination when READ_NOTIFY on | Customer with Case fallback / Case-wins-on-diverge |
| OA history when READ_LINE on | Customer → Cases with Case fallback |
| Merge | Manual only (M8.4) |
| Drift detection | Offline reconcile (M8.7) |
| Flag promotion | Human (M8.8) |

## Governance model

### Roles

| Role | Authority |
|------|-----------|
| **Operator** | Run reconcile scan, shadow metrics dumps, phase checklist; propose flag changes |
| **Reviewer** | Sign go/no-go; approve Phase advances |
| **On-call** | Execute flag-only rollback; page on wrong-recipient / send spike |
| **Identity steward** | Approve M8.4 merges; ticket `line_diverge`; decide identityDecisions |

### Decision rights

| Decision | Who | Tool |
|----------|-----|------|
| Enable/disable Customer flags | Reviewer + Operator | Env deploy per M8.8 |
| Apply allow-listed repair (`link_missing`, fill empty LINE) | Operator after dry-run | M8.7 repair `--mode=write` |
| Fix `line_diverge` | Identity steward | Manual / M8.4 — **never auto** |
| Merge Customers | Identity steward | M8.4 execute (MERGE_ENABLED) |
| Change matching rules | Architecture change request | New milestone — not M8.9 ops |

### Matching policy (permanent)

- Exact only: LINE → phone → email  
- No fuzzy; no name auto-match / auto-merge  
- Phone/email normalized

## Dual-write & denormalization policy (steady state)

| Field | Policy |
|-------|--------|
| Case `LINE User ID` | **Retain indefinitely** — fallback, history, safety, M8.6 Case-wins-on-diverge |
| Case Customer ID / Page ID | Required link once dual-write ON; backfill/reconcile keep healthy |
| Customer LINE / phone / email | Identity SSOT when flags enabled |
| Notification status / tokens / scores | Case only — never migrate to Customer |

**M8.9 does not authorize** deleting Case LINE or collapsing notification onto Customer.

After full M8.8 Phase 6 (if/when enabled):

- Dual-write **stays ON** in steady state (prevents new drift)  
- Shadow flags may be OFF once primary is stable  
- Reconcile remains scheduled (see cadence)

## Recurring ops cadence

| Cadence | Activity |
|---------|----------|
| **Weekly** | `run-customer-reconcile.js scan`; archive summary; triage orphans / diverge |
| **Weekly** | `run-customer-merge.js detect` (or after known identity incidents) |
| **Daily while shadowing** | LINE/notify metrics dump + log review (M8.8 phases 3/5) |
| **Per deploy** | `check-customer-rollout-gates.js`; confirm flags match intended phase |
| **Monthly** | Review soft phone/email conflicts; ticket backlog for steward |
| **On incident** | Rollback card first; then reconcile / merge as needed |

SLAs (suggested):

- Unticketed `orphanCustomerLink`: fix or ticket within **2 business days**  
- Unticketed `lineDiverge`: ticket within **1 business day**; no auto-repair  
- Merge queue tickets: steward response within **5 business days**

## Steady-state monitoring (post-rollout)

Keep using:

- Reconcile counters + gates  
- `[customer_line_read]` / `[customer_notify_read]` / `[line_close_notify]`  
- Dual-write success/error  
- Case notification `sent`/`failed` rates  

Alert ideas (ops config — not code in this design):

- mismatch rate spike  
- conflict &gt; 0  
- dual-write error rate  
- wrong-recipient suspicion → immediate NOTIFY off

## Explicit non-goals (require M9+ / new ADR)

| Non-goal | Why |
|----------|-----|
| Auto-merge | Wrong-recipient / identity risk |
| Remove Case LINE | Breaks fallback and diverge safety |
| Move Offer/Workflow/Feedback/Report/Notification state to Customer | Violates Case aggregate root |
| Fuzzy match | ADR forbidden |
| App-driven flag auto-promote | Human governance only |
| Customer-owned booking history UI as new SSOT | Product/M9+ |

## Definition of done — M8 program

M8 Customer Domain is **architecturally complete** when:

1. M8.1–M8.8 artifacts exist (code + ops) — **met**  
2. Governance cadence documented (M8.9) — **this design**  
3. Production flags may still be OFF — **acceptable**; enablement is ops, not a missing model  

M8.9 “implementation” is **governance documentation + optional calendarized checklist**, not new identity runtime.

Program **operationally complete** when (optional future):

- M8.8 Phase 6 done in production **or** conscious decision to remain Case-primary with dual-write only  
- Weekly reconcile green for N consecutive weeks
