## Purpose

Long-term Care operating model: how we **monitor, review, decide, and improve** after launch — without moving ownership or automating policy.

---

## Ownership boundaries (locked)

| Domain | Owns | Does not own |
|--------|------|----------------|
| **Case** | Ops SSOT; service history; result notification state | Care policy, Care Audit, Care outcomes |
| **Customer** | Identity only (LINE / phone / email; consent) | Care campaigns; ops workflows |
| **Care** | Policy, events, audits, outcomes, CDRs | Case result-send; Customer merge / identity expansion |

No ownership movement between Case, Customer, and Care.

---

## Steady-state operating model

```text
Launch complete (M9.4 Phase 4)
    ↓
Monitor (delivery + outcomes + complaints)
    ↓
Review outcomes (weekly classify)
    ↓
Create CDR (if propose_change)
    ↓
Approve (Reviewer)
    ↓
Controlled update (Operator)
    ↓
Validate (dry-run / observe)
    ↓
Monitor …
```

**Incident interrupt:** flag rollback first → investigate → optional post-incident CDR  
See `docs/M9.5_CARE_INCIDENT_OPERATIONS.md`.

Until launch completes, the same loop applies to dry-run observation; **SEND stays M9.4-gated**.

---

## Recurring workflow

### Weekly

1. Gate / readiness / pattern / outcome scripts (observe-only)  
2. Classify: `healthy` | `investigate` | `propose_change` (`docs/M9.3_POLICY_REVIEW_RUNBOOK.md`)  
3. If `propose_change` → draft CDR (`docs/M9.5_CARE_CDR_OPERATIONS.md`)  
4. Confirm Case result-send health unchanged  

Checklist detail: `docs/M9.1_OPERATIONS_CADENCE.md`.

### Monthly

- Volume vs Case population  
- Copy / tone  
- Consent samples  
- Open CDR follow-ups (`applied` criteria met?)  
- On-call still knows rollback cards  

### Per deploy

- Flags match intended phase  
- Relevant Care fixture tests green  

### Per CDR apply

- Apply only approved `changeDetail`  
- Dry-run validate when material  
- Prefer ≥ **7 days** before another **same-lever** CDR (unless incident)
