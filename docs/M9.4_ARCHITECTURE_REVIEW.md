## Goal

Design the **final operational path** before any `CARE_LIFECYCLE_SEND` production usage.

M9.4 is **production rollout readiness** — not a new Care feature:

1. Validate Care is ready for live sends  
2. Define production approval gates (beyond M9.1 scaffolding)  
3. Define first-send safety controls and expansion  
4. Define monitoring + rollback ownership  
5. Define steady-state operation after launch  

M9.4 does **not** invent new campaigns, auto-targeting, or ML. It does **not** enable flags in this design turn.

---

## Current architecture

| Layer | State |
|-------|--------|
| Case | Ops SSOT; result notification lifecycle unchanged |
| Customer | Identity only |
| Care Lifecycle | Implemented (`care.reinspection_6mo`); SEND OFF |
| Care Audit | Separate from Case notification state |
| Outcomes (M9.2) | Read-only reporting available; flags OFF |
| Governance (M9.3) | CDR + review runbook; human approval for policy changes |
| Runtime flags | All CARE / outcome flags **false**; no production Care messages sent |

---

## Architecture principles (locked)

```text
Case          = operational SSOT
Customer      = identity only
Care          = separate policy + audit domain
CareAudit     ≠ Case notification state
Policy change = human CDR (M9.3)
SEND enable   = human go/no-go (M9.1 + M9.4 gates)
Rollback      = flag-only
```

```text
Phase 0 OFF
  → Phase 1 ENABLED
  → Phase 2 dry-run observation
  → M9.4 production readiness sign-off
  → Phase 3 limited SEND
  → observe + expand
  → Phase 4 steady state
```

M9.4 **wraps** M9.1 phases 2→3→4 with explicit readiness criteria, ownership, and post-launch monitoring — it does not replace the M9.1 sequence.

## 1. Production readiness gates

All gates must pass **before** first production `CARE_LIFECYCLE_SEND=true`. Completing gates does **not** auto-enable flags.

### 1.1 Care eligibility accuracy

| Criterion | Pass |
|-----------|------|
| Event scope | Only `care.reinspection_6mo` (no new campaigns) |
| Anchor quality | Spot-check ≥ **20** dry-run rows (or all): correct Case, plausible service/completion anchor |
| False positives | **0** unticketed “should not remind” after steward/reviewer review |
| Too-recent / window | `too_recent` / timing skips explained; timing changes only via CDR |
| Population sanity | Eligible / dry-run volume within ops-expected band vs Case base |

### 1.2 Dry-run report quality

| Criterion | Pass |
|-----------|------|
| Count | ≥ **3** successful dry-run scans archived |
| Window | ≥ **7 days** (or ≥ **14 days** if low volume) |
| Artifacts | `tmp/care-lifecycle/<runId>.json` + `latest.json` retained |
| Gate script | `check-care-rollout-gates.js` reviewed; phase consistent with ENABLED + SEND false |
| Pattern scanner | `check-care-patterns.js` warnings triaged (advisory; unexplained spikes hold SEND) |

### 1.3 Consent handling

| Criterion | Pass |
|-----------|------|
| Skip path | `consent_line_false` (and equivalents) appear and are honored in samples |
| No override | No plan to “push anyway” when consent false |
| Steward | Identity steward available for consent / wrong-recipient edge cases |

### 1.4 LINE destination safety

| Criterion | Pass |
|-----------|------|
| Destination | Case LINE (default); if `READ_NOTIFY` ever on, Case-wins-on-diverge still applies — **not required** for Care launch |
| Sample | Dry-run rows with destination present; `no_line` skips explained |
| Copy | Thai **care** tone approved (not marketing blast) |
| Mock vs live | Production uses real LINE token path only when intentionally live; `LINE_MOCK_SEND` not masking prod SEND |

### 1.5 Idempotency verification

| Criterion | Pass |
|-----------|------|
| Re-scan | Second dry-run does not invent duplicate planned sends for same idempotency key |
| Index | Idempotency index retained (do not delete as “cleanup”) |
| Runner | **Single** cron / operator runner documented (no multi-instance double fire) |

### 1.6 Audit completeness

| Criterion | Pass |
|-----------|------|
| File audit | Every dry-run / future send leaves Care Audit trail (`events.jsonl` / run report) |
| Separation | Reports confirm Case `notificationStatus` / `resultSentAt` **unchanged** by Care |
| Notion | Optional; file audit required for launch |
| Immutability | No process that rewrites historical audit rows |

### 1.7 Outcome tracking readiness

| Criterion | Pass |
|-----------|------|
| Report CLI | `run-care-outcome-report.js` runnable; team knows path to `latest-outcome-report.json` |
| Cadence | Weekly review includes outcomes + M9.3 runbook classification |
| CDR path | Policy/template/timing changes require CDR before apply |
| Flags | Outcome flags may stay **false** at SEND launch if reports still run read-only on files; enabling `CARE_OUTCOME_*` is **independent** and optional — never a substitute for SEND go/no-go |
| Attribution | Exact `customerId` / LINE only; no fuzzy learning |

### 1.8 Global (carry forward from M9.1)

| Criterion | Pass |
|-----------|------|
| Fixture tests | `test-care-lifecycle.js` (+ outcomes/governance tests as relevant) green |
| Case result-send | Baseline healthy and independent of Care |
| Rollback | On-call knows `docs/M9.1_ROLLBACK_CARD.md` |
| Checklist | `docs/M9.1_GO_NO_GO_CHECKLIST.md` Phase 3 section ready to sign |

## 2. First production send strategy

### 2.1 Pilot scope

| Constraint | Rule |
|------------|------|
| Event | `care.reinspection_6mo` only |
| Audience | Whatever eligibility yields — **no** ad-hoc marketing list; safety via `--limit=` |
| Environment | Production only after staging confidence (if staging exists) + signed checklist |
| Customer Domain | Not required; do not enable M8 flags “for Care” |

### 2.2 Sequence (locked shape)

```text
dry-run gates passed
    ↓
internal approval (Operator + Reviewer + On-call ack)
    ↓
CARE_LIFECYCLE_SEND=true
    ↓
limited SEND  --limit=10
    ↓
observe (Care Audit + complaints + pattern scan)
    ↓
approval checkpoint
    ↓
--limit=50
    ↓
observe
    ↓
approval checkpoint
    ↓
uncapped / cron steady-state
```

Never skip dry-run. Never jump to uncapped without **10 then 50**.

### 2.3 Approval checkpoints

| Checkpoint | Required before |
|------------|-----------------|
| A — Production readiness | First `SEND=true` |
| B — After limit 10 | Expanding to 50 |
| C — After limit 50 | Uncapped / cron |
| D — Steady-state | Ongoing weekly (M9.1 cadence + M9.3) |

Each checkpoint: Reviewer sign-off; unexplained fail/wrong-recipient = **NO-GO** (rollback SEND).

### 2.4 Observe window between ladder steps

Minimum recommendation (lock in implementation plan):

| Step | Observe before next |
|------|---------------------|
| After `--limit=10` | ≥ **24h** + Care Audit review + no wrong-recipient tickets |
| After `--limit=50` | ≥ **48–72h** + skip/fail mix stable |
| Uncapped | Cron documented; weekly cadence active |

Exact hours are an **open decision** below; principle is **human observe between expansions**.

## 3. Monitoring

### 3.1 Delivery metrics

| Metric | Source | Owner |
|--------|--------|-------|
| sent / failed / skipped / dry_run | Care run `latest.json` | Operator |
| failed share | Audit + `check-care-patterns.js` | Operator / On-call |
| Idempotent suppress | `already_sent` / index | Operator |

### 3.2 Failure alerts (process, not platform mandate)

| Trigger | Action |
|---------|--------|
| Failed share spike (e.g. ≥20% with denom ≥5) | Pause SEND; investigate LINE/template |
| Wrong recipient / care spam complaint | **Immediate** `CARE_LIFECYCLE_SEND=false` |
| Suspected Case notification mutation | SEND+ENABLED off; escalate (should be impossible) |

M9.4 does not require a new alerting product; pager ownership may reuse existing ops channels.

### 3.3 Skip reason monitoring

Weekly: mix of `no_line`, `consent_line_false`, `too_recent`, `missing_anchor`, `already_sent` must remain **explainable**. Unexplained mass skips → investigate before expansion / CDR.

### 3.4 Duplicate prevention checks

- Re-run send/dry-run: no duplicate customer-facing push for same idempotency period  
- Confirm single runner  
- Never delete idempotency index during incidents  

### 3.5 Customer complaints / opt-out

| Signal | Handling |
|--------|----------|
| Complaint | Rollback SEND first; retain audits |
| Consent withdraw | Customer consent path; future Care skips — no Case notification rewrite |
| Opt-out postback (if ever added later) | Out of M9.4 launch scope unless already shipped |

### 3.6 Outcome review cadence

| Cadence | Action |
|---------|--------|
| Weekly | Outcome report + pattern scan + M9.3 classification |
| After each ladder step | Snapshot metrics into checkpoint notes / optional CDR `no_change` |
| Monthly | Effectiveness governance + copy/consent |
| Policy change | CDR required (template/timing/throttle/eligibility) |

## 4. Rollback

### 4.1 Flag-only (locked)

```text
1. CARE_LIFECYCLE_SEND=false
2. CARE_LIFECYCLE_ENABLED=false    # if evaluation / cron must stop
```

Redeploy/restart per host. Verify with `check-care-rollout-gates.js`.

### 4.2 Ownership

| Role | Duty |
|------|------|
| On-call | Execute flag rollback immediately |
| Operator | Preserve Care Audit / reports; draft post-incident notes |
| Reviewer | Approve re-entry to Phase 2/3 only via go/no-go |
| Identity steward | Consent / wrong-recipient follow-up |

### 4.3 Explicit non-actions

| Forbidden | Why |
|-----------|-----|
| Case rewrite / `notificationStatus` undo | Care ≠ Case result-send |
| Customer rollback / mass unlink | Identity out of scope |
| Audit deletion | Forensics + anti-resend |
| Identity fuzzy-merge | Architecture violation |
| Enabling Customer Domain as “fix” | Separate program (M8.8) |

Optional post-incident **CDR** after stability — never a substitute for immediate flag rollback.

---

## 5. Steady-state after launch (Phase 4)

Once uncapped (or cron) is approved:

1. Follow `docs/M9.1_OPERATIONS_CADENCE.md` + M9.3 review runbook  
2. Keep Care Audit and outcome reports as SSOT for Care health  
3. Any template/timing/throttle/eligibility change → **CDR** before apply → dry-run validate when material  
4. SEND remains reversible anytime via rollback card  
5. Case result-send and Customer Domain remain independent  

Steady-state is **operations**, not automatic optimization.

---

## 6. Flags & independence

```text
CARE_LIFECYCLE_ENABLED   # Phase 1+
CARE_LIFECYCLE_SEND      # Phase 3+ only after M9.4 readiness + M9.1 checklist
CARE_OUTCOME_TRACKING    # optional; independent of SEND
CARE_OUTCOME_REPORT      # optional; independent of SEND
```

M9.4 **may** recommend enabling outcome observation for production learning, but must **not** couple outcome flags to SEND approval. Default remains false until operators choose.

## 7. Risks

| Risk | Mitigation |
|------|------------|
| Skipping dry-run under schedule pressure | Hard sequence; checklist sign-off |
| Jumping to uncapped | Limit ladder + checkpoints B/C |
| Using M9.3 “healthy” to force SEND | SEND only via M9.1/M9.4 gates |
| Double cron fire | Single-runner doc + idempotency |
| Treating Care as Case reminder field | Boundary tests + rollback non-actions |
| Deleting audits after complaint | Rollback card forbids |
