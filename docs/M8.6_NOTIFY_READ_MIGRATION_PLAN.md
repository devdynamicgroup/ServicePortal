# M8.6 — Notification Identity Read Migration Plan

**Status:** Architecture design (not implemented)  
**Flags:** `CUSTOMER_DOMAIN_READ_NOTIFY` default **OFF**; requires `CUSTOMER_DOMAIN_ENABLED=true`  
**Out of scope:** Moving Notification ownership off Case; changing LINE push payload; webhook; Offer/Workflow; enabling `READ_LINE` (already M8.5)

---

## Scope

**In scope**

- Resolve **LINE User ID for outbound push** (result send / close notify) via Customer when flagged
- Shadow compare: Case LINE vs Customer LINE
- Feature-flagged primary Customer identity with Case fallback
- Metrics + PII-safe logging

**Out of scope**

- Changing notification **state machine** ownership (status, resultSentAt, messageId stay on Case)
- Changing Flex/text message format or score-card URLs
- LINE webhook / OA reply path (M8.5)
- Removing Case `LINE User ID` denormalized fields
- Phone / email / name lookup to find a push target

---

## Current state (after M8.5)

```text
executeSendCaseResult(job)
  → lineUserId = job.line.userId          // Case denormalized LINE
  → sendCaseResultNotification(job, …)    // uses job.line.userId again
  → LINE push
```

Notification **status** and audit fields remain on Case. Only the **destination identity** is in scope for M8.6.

---

## Target read path

```text
Case (ops root for this send)
  → Case.customer.id (Customer ID link)
  → Customer (exact customerId)
  → Customer.lineUserId
  → LINE push destination
```

Fallback (always available in M8.6):

```text
Case.line.userId
```

---

## Runtime modes

| Mode | Flags | Push destination | Side work |
|------|-------|------------------|-----------|
| case_only | default / READ_NOTIFY off | `job.line.userId` | none |
| shadow | ENABLED + READ_NOTIFY_SHADOW + !READ_NOTIFY | Case LINE | resolve Customer LINE; compare; metrics |
| primary | ENABLED + READ_NOTIFY | Customer LINE when safe (see policy); else Case | metrics |

Suggested shadow flag (mirror M8.5): `CUSTOMER_DOMAIN_READ_NOTIFY_SHADOW` default false.

---

## Destination resolution policy (primary)

1. Load Case (already in hand).
2. If Case has `customer.id`:
   - `findByCustomerId` (exact business id only).
   - If Customer found and `lineUserId` non-empty:
     - If Case LINE empty → **use Customer** (fills missing denormalized field for send).
     - If Case LINE equals Customer LINE → **use Customer** (identity SSOT; same value).
     - If Case LINE ≠ Customer LINE → **mismatch/conflict metric; use Case LINE** (do not guess; protect wrong-recipient risk).
   - If Customer missing / no LINE / error → **Case LINE fallback**.
3. If Case has no `customer.id` → **Case LINE only**.
4. If resolved LINE empty → existing `skipped` / `no_line_user_id` behavior.

**Forbidden:** phone, email, name, fuzzy, or “any Case for this Customer” fan-out to pick a LINE.

---

## Rollout stages

| Stage | Flags | Behavior |
|-------|-------|----------|
| A | all OFF | Today |
| B | ENABLED + DUAL_WRITE (recommended) | Identity stays fresh on link/create |
| C | + READ_NOTIFY_SHADOW | Compare only; Case still sends |
| D | READ_NOTIFY primary | Customer destination when policy allows; Case fallback |
| E | Observe | Acceptance gates; keep Case LINE fields |

**Prerequisite:** Prefer M8.5 shadow/primary acceptance healthy before enabling notify primary in production (optional but strongly recommended).

---

## Rollback

1. `CUSTOMER_DOMAIN_READ_NOTIFY=false` (+ shadow false) → immediate Case-only destination.
2. No data rollback.
3. Notification status history on Case unchanged.
