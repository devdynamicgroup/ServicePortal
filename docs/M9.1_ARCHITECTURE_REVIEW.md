## 1. Care rollout phases (locked)

```text
Phase 0  CARE OFF
Phase 1  CARE_LIFECYCLE_ENABLED=true   (SEND still false)
Phase 2  DRY_RUN observation           (scan --mode=dry-run)
Phase 3  CARE_LIFECYCLE_SEND=true      (first live care pushes)
Phase 4  Steady-state cadence
```

Never skip Phase 2. Never enable SEND without a completed dry-run window.

`CUSTOMER_DOMAIN_*` remain independent — M9.1 does **not** require or enable them. Destination stays Case LINE unless ops already enabled `READ_NOTIFY` under M8.8.

## 2. Dry-run observation gates

### Commands

```bash
node scripts/test-care-lifecycle.js
node scripts/run-care-lifecycle.js scan --event=reinspection_6mo --mode=dry-run
```

Archive: `tmp/care-lifecycle/<runId>.json` + `latest.json`

### Pass criteria (staging → production)

| Gate | Pass |
|------|------|
| Fixture tests | Green |
| Dry-run runs | ≥ **3** successful scans over ≥ **7 days** (or ≥ **14 days** if volume low) |
| Sample review | Spot-check ≥ **20** `dry_run` rows (or all if fewer): Case anchor correct; LINE present; care tone OK |
| Skip reasons | `missing_anchor` / `too_recent` / `no_line` / `consent_line_false` / `already_sent` explained |
| False positives | Unticketed “should not remind” cases = **0** after steward review |
| Case notification | Confirmed **unchanged** in reports (`notificationStatusBefore === After`) |
| Idempotency | Re-scan does not invent duplicate planned sends for same key |
| Volume sanity | Eligible count within expected band vs Case population (ops judgment + ticket if spike) |

### Fail → do not advance to SEND

- Unexplained mass eligibility  
- Wrong Case anchors in sample  
- Any path writing Case `notificationStatus`  
- Dry-run CLI errors / incomplete reports

## 3. Production enablement gates (before SEND)

| Gate | Requirement |
|------|-------------|
| Phase 2 dry-run gates | Passed and signed |
| On-call | Knows care rollback card |
| Copy | Thai care tone approved (not marketing blast) |
| Consent | `consentLine === false` skip verified in dry-run sample |
| Cron | External scheduler documented; single runner (no multi-instance double fire) |
| Limit | First prod SEND runs with `--limit=` cap (e.g. 10 → 50 → uncapped) |
| CARE Audits | File audit required; Notion DB optional but recommended for durable ops |
| Customer Domain | No dependency; if `READ_NOTIFY` on, confirm Case-wins-on-diverge still applies |

## 4. Operational controls

### Roles (reuse M8.9 RACI)

| Role | Care duty |
|------|-----------|
| Operator | Dry-run scans, archive reports, propose SEND |
| Reviewer | Sign go/no-go for SEND |
| On-call | Disable SEND/ENABLED on incident |
| Identity steward | Consent / wrong-recipient edge cases |

### Controls before/at SEND

1. **Flag split:** ENABLED without SEND = observe only  
2. **Graduated limit** on first live runs  
3. **Idempotency index** retained across runs  
4. **Separate Care Audit** — never Case result-send fields  
5. **Rollback card** (flag-only)  
6. **No new event types** in M9.1  

### Steady-state cadence (Phase 4)

| Cadence | Action |
|---------|--------|
| Weekly | Dry-run or limited scan; review skips + sent/failed |
| Monthly | Eligible volume trend; copy/consent review |
| Per deploy | Confirm CARE flags match intended phase |
| Incident | SEND off first → investigate Care Audit / LINE logs |

---

## 5. Monitoring

| Signal | Source |
|--------|--------|
| Dry-run / sent / skipped / failed counts | Run report `counts` |
| Skip reason mix | `results[].reason` |
| LINE push outcome | Care Audit `sent`/`failed` + LINE logs |
| Case notification integrity | Report fields `notificationStatusBefore/After` |
| Double-send attempts | Idempotency index `already_sent` skips |

Alert ideas (ops, not code in this design): failed rate spike; eligible count spike; any Case notification mutation (should be impossible).

---

## 6. Rollback (flag-only)

```text
1. CARE_LIFECYCLE_SEND=false
2. CARE_LIFECYCLE_ENABLED=false   # if evaluation must stop
```

- Result-send / OA history / Customer Domain flags **untouched**  
- No Case rewrite; no Care Audit deletion required  
- Idempotency index retained (prevents re-spam after re-enable in same period)

## Risks

| Risk | Mitigation |
|------|------------|
| First SEND spams customers | Graduated `--limit`; dry-run window; idempotency |
| Confused with result-send | Separate audit; gate checks notification untouched |
| Cron double-fire | Single cron; idempotency keys |
| Enabling SEND without ENABLED | Config validation + CLI refuse |
| Pressure to skip dry-run | Phase lock in runbook |
