## Goal

Define how Care **improves safely** using measured outcomes.

M9.3 is **operational learning**, not automation:

1. Review care effectiveness from outcome reports  
2. Improve templates / timing / eligibility **manually**  
3. Detect operational issues early (delivery, attribution, volume)  
4. Prepare a documented path toward future Care maturity  

M9.3 does **not** enable `CARE_LIFECYCLE_SEND`, does **not** add new campaigns by default, and does **not** auto-mutate policy.

## Architecture principle (locked)

```text
Care Event
    ↓
Care Audit
    ↓
Outcome Signals
    ↓
Human Review
    ↓
Policy Adjustment
```

Learning is a **human-gated Care-domain loop**. Outcomes inform operators; operators change policy/config with the same discipline as M9.1 go/no-go. Nothing in this loop writes Case `notificationStatus` / `resultSentAt`.

| Concern | Owner in M9.3 |
|---------|----------------|
| Outcome measurement & reports | **Care** (M9.2; read-only consume) |

| Identity / consent | **Customer** — untouched except read for consent skips |
| Auto policy mutation / ML | **Out of scope** |

## 2. Learning loop (detail)

### 2.1 Inputs (already available or planned observe-only)

| Input | Source | Use |
|-------|--------|-----|
| Delivery mix | Care Audit / outcome report `delivery.*` | Health of push path |
| Response mix | Outcome report `response.*` | Effectiveness signal |
| Rebook rate | `rebooked / sent` (30d attribution) | Primary “did care work?” proxy |
| Skip reason mix | Care run reports | Eligibility / consent / LINE coverage |
| Failures | Audit `failed` + LINE errors | Operational defects |
| Dry-run vs sent gap | Phase 2 vs Phase 3 archives | Calibration before/after SEND |

Exact join only for rebook: `customerId` **or** LINE User ID (M9.2). No fuzzy / name attribution in learning.

### 2.2 Human review (required)

Weekly (extends M9.1 cadence):

```text
run / open latest-outcome-report.json
  → classify: healthy | investigate | propose change
  → if propose change: write Care Decision Record (CDR)
  → apply only after reviewer sign-off
  → next dry-run validates change (SEND still gated by M9.1)
```

Monthly:

- Trend rebook rate and skip mix vs Case population  
- Copy / tone fitness (Thai care, not blast)  
- Confirm Case result-send health independent of Care  

### 2.3 Policy adjustment (allowed levers)

| Lever | Example | Gate |
|-------|---------|------|
| Eligibility timing | `CARE_REINSPECTION_DAYS` | Documented change + dry-run sample |
| Template version | `templateVersion` / copy text | Tone approval; bump version in audit |
| Throttle / limit | `--limit=` ladder, cron frequency | M9.1 SEND gates if live |
| Observation windows | Response 7d / rebook 30d docs | Architecture note if changed |
| Skip policy clarity | Consent / no_line handling | Steward if identity-adjacent |

**Not allowed as silent automation:** changing eligibility code thresholds from report metrics without a CDR; enabling SEND because rebook rate “looks good” without M9.1 checklist.

## 3. Care Decision Record (CDR)

Lightweight ops artifact (markdown or Notion page — design choice; not a new runtime store).

Minimum fields:

| Field | Purpose |
|-------|---------|
| Date / author / reviewer | Accountability |
| Metric snapshot | sent, failed, skip mix, rebookRate, sample size |
| Finding | What looks wrong or improvable |
| Decision | No-change / template / timing / throttle / pause SEND |
| Rollback | How to undo (flag, prior template version, prior env) |
| Follow-up | Next dry-run date / success criteria |

CDRs are the **audit trail of learning**, parallel to Care Audit as the audit trail of sends.

---

## 4. Operational issue detection

Treat outcome + run reports as **early-warning**, not alerts that auto-fire Care.

| Pattern | Likely issue | First action |
|---------|--------------|--------------|
| Spike `failed` | LINE token / API / template | Pause SEND if live; M9.1 rollback card |
| Spike `no_line` / `consent_line_false` | Coverage or consent data | Steward sample; do not fuzzy-fill |
| Spike `already_sent` | Cron double-run or key drift | Confirm single runner |
| Near-zero rebook after adequate `sent` + window | Copy / timing / wrong audience | CDR → dry-run copy/timing test |
| Sudden eligible volume jump | Eligibility bug or Case data shift | Hold SEND; sample anchors |
| Rebook attribution looks “too high” | Window too wide or join bug | Tighten review; exact-join audit |
| Case `notificationStatus` movement correlated with Care | Boundary violation | Stop Care work; investigate Case path |

M9.3 documents these patterns; it does **not** require a new alerting platform.

---

## 5. Effectiveness review rubric

Use for human classification only:

| Signal | Weak | Acceptable | Strong (interpret with volume) |
|--------|------|------------|--------------------------------|
| Delivery success | High fail rate | Mostly `sent` / explained skips | Stable `sent` + low unexplained fail |
| Response | Almost all `no_response` after window | Mix with some rebook/UTM | Meaningful rebook rate vs baseline organic rebook |
| Ops hygiene | Unexplained skips / wrong anchors | Explained skip mix | Stable mix + clean samples |

**Baseline caveat:** Until SEND is enabled under M9.1, effectiveness reviews use **dry-run quality** + historical Case organic rebook context — not live care ROI. M9.3 must not invent SEND pressure from dry-run-only metrics.

## 6. Future Care maturity (prepare only)

M9.3 prepares the **operating system** for later maturity; it does not implement these:

| Horizon | Idea | Prerequisite |
|---------|------|--------------|
| Later | Second event type (e.g. post-service tip) | Stable SEND + CDR history + M9.1 gates reused |
| Later | Separate `CareOutcomeEvent` store (M9.2 Option B) | Volume / history needs |
| Later | Care postback ack signals | OA intent priority review |
| Later | Dashboard widgets for ops | Still Care-owned metrics; not Case notification UI |
| Out | Auto-tuning eligibility from ML | Explicit future program; not M9.3 |

Document maturity as a **roadmap appendix**, not an implementation backlog in this milestone.

## 7. Flags & runtime

M9.3 **adds no requirement to enable** existing flags:

```text
CARE_LIFECYCLE_ENABLED   # unchanged; default false
CARE_LIFECYCLE_SEND      # unchanged; default false — never enabled by M9.3
CARE_OUTCOME_TRACKING    # optional observe; independent of SEND
CARE_OUTCOME_REPORT      # optional; CLI may read files without it
```

If a later implementation plan wants a docs-only or cron reminder flag (e.g. “weekly learning checklist due”), it must **not** gate or imply SEND. Prefer process (cadence checklist) over new runtime flags unless tooling clearly needs one.

## 10. Risks

| Risk | Mitigation |
|------|------------|
| Learning used as pretext to enable SEND | Explicit non-goal; M9.1 checklist remains sole SEND path |
| Auto-tuning from thin samples | CDR + minimum sample guidance; no auto-mutate |
| Mis-attributed “success” | Exact join; 30d window; organic rebook baseline caveat |
| Scope creep into analytics platform | Cadence + CDR + existing report CLI only |
| Polluting Case notification state | Forbidden; regression tests / boundary review |
| Template thrash | Version bumps + one change per CDR cycle |

## 11. Non-goals (M9.3)

- Enabling `CARE_LIFECYCLE_SEND` or production Care rollout  
- New care campaigns as the primary deliverable  
- Automatic policy mutation / ML optimization  
- Customer identity redesign / fuzzy match  
- Merging Care outcomes into Case result-send fields  
- Dashboard/Framer redesign  
- Moving Booking / Workflow / Offer / Feedback / Report under Care  
- Implementing M9.4+ maturity items in this milestone
